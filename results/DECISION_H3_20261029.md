# DECISION H3 — Q6_K W4R4 T=4 : NO-GO microbench (29/10)

## Question
Le kernel Q6_K `mul_mat_vec_q` (type14, ~28.9–31.5 % du temps GPU-kernel decode,
cible in-scope dominante) est-il optimisable via un levier **non-trafic**
(hoist du dépaquetage 4×4) sans toucher au volume de lecture des poids ?

## Candidat H3
- **Idée** : même grid/block/boucle K que prod (parallélisme identique, 0 %
  de changement de trafic poids), mais le bloc poids (q6_K, 4 lignes) et le
  bloc activation (q8_1, 4 tokens) d'un (lane,kbx) sont chargés **une fois**
  par (lane,kbx), puis les 16 dp4a partent des regs.
- Prod recharge le bloc poids (i,kbx) 4× (une fois par j) et le bloc act
  (j,kbx) 4× (une fois par i) par (lane,kbx) → 16 appels `vec_dot_q6_K_q8_1`,
  chacun refaisant l'extract `get_int_b2/b4` + shift/AND.
- Gate : `GGML_CUDA_Q6_H3=1`, dispatch Q6_K W4R4 T=4, Volta, pas ids/fusion,
  `nchannels_dst==1 && nsamples_dst==1` (sécurité : kernel mono channel/sample).
- **Pas de modification du .so prod** : build dans le fork dual-arch, candidat
  `libggml-cuda-dual.so`, A/B via `MB_MMVQ_SO`.

## Candidat (artefacts)
- Kernel : `mul_mat_vec_q6_k_w4r4_h3` (patch `scratch/proto_v2/patch_h3.py`,
  idempotent + `--revert` ; backup clean 8035caf4 `mmvq.cu.fork-8035caf4.bak`).
- `.so` candidat : `dual-arch/lib/libggml-cuda-dual.so.h3-20261029`
  md5 `014d940eb…` (build 29/10 14:44, sm_70+sm_61, 150 ELF sm_70).
- Prod intact : `8035caf4…` (vérifié avant/après).
- Regs H3 : **96**, STACK 0, LOCAL 0, SHARED 6144 B → **0 spill**,
  `__launch_bounds__(128,5)` → 5 blocks/SM = **identique à prod**
  (prod 96 regs : le hoist n'a rien sauvé — la pression register vient des
  16 accumulateurs `tmp[4][4]` + la réduction warp, pas des buffers de hoist).

## Validation numérique (obligatoire avant timing)
`mb_mmvq` (dlopen prod vs H3, même RNG seed 987654+K) + dump hex de la sortie :
- `q6_f17408x5120` T=4 : **BIT-EXACT** (dump identique prod vs H3)
- `q6_f5120x17408` T=4 : **BIT-EXACT**
- T=1 : H3 non dispatché (case ncols_dst==4), 0 impact.
→ H3 est **bit-exact** avec prod (pas seulement "proche") : même dp4a, même
point d'accumulation, même ordre en kbx, 0 spill.

## Résultats A/B microbench (interleaved 6×, 60 iters, médiane)

| shape (T=4) | prod µs | H3 µs | gain | verdict |
|---|---:|---:|---:|---|
| **q6_f17408x5120** (dominante, 36.9 % prod) | 135.2 | 132.1 | **+2.29 %** | < 5 % |
| q6_f5120x17408 | 134.1 | 135.2 | −0.82 % | noise |

- Seuil de go : **≥ 5 %** sur la shape dominante (consigne note).
- +2.29 % (≈ 3.1 µs sur 135 µs) est réel (reproductible, bit-exact) mais
  **sous le seuil**. Sur q6_f5120x17408 : nul/négatif.

## Pourquoï 2.29 % seulement (et pas 6–10 %)
1. **Le dépaquetage n'était pas le bottleneck** : NCU recon2 = DRAM 59 %,
   SM 66 %, NoElig 33 %, occ 27 %. Le kernel est **latency/memory-bound**,
   pas ALU-bound. Enlever les re-extracts `get_int_b2/b4` (quelques ALU/LSU
   par (lane,kbx,j,i)) ne réduit ni le trafic (inchangé), ni la pression
   register (96 → 96), ni la latence mémoire (inchangée).
2. **0 spill** : prod ne se spillait pas non plus (LOCAL 0) ; le gain de
   H3 est seulement la suppression d'instructions d'extract redondantes,
   masquées par la latence mémoire dominante.
3. Le vrai limiter (regs 96 → 5 blocks/SM) vient des **accumulateurs
   `tmp[4][4]` + la réduction warp de 4 warps** — pas du hoist.

## Verdict
**NO-GO microbench** (2.29 % < 5 %). Pas d'A/B applicatif (Phase 5 annulée).
Le levier "hoist du dépaquetage" est **clos** pour le Q6_K W4R4 T=4.

## Conséquences pour la mission
- `mmvq_CLOS_note.md` (levier trafic clos) **s'étend** : le levier
  "re-dépaquetage / instruction-level hoist" est aussi clos (0 spill,
  ALU pas le limiter).
- Les 3 familles de leviers kernel Q6_K W4R4 testées (trafic : clos ;
  nwarps : clos ; hoist unpack : clos) n'atteignent pas 5 %.
- **Prochaine direction (si on continue sur le GEMV Q6_K)** :
  (a) attaquer les **96 regs** = réduire la réduction warp (4→2 warps avec
  rows_per_block adaptée) ou la partition K (moins de kbx par lane),
  (b) accepter que le Q6_K W4R4 est quasi-optimal pour cette forme de
  dispatch et re-scope la cible (Q8_0 11.2 % ou Q5_K 8.3 % — plus petits
  mais mêmes limiters),
  (c) si le but est le **throughput applicatif** et non le kernel seul :
  les 30 % restants sont hors GEMV (attention q8v14partial hors périmètre
  poids, shortlist, quantize).
