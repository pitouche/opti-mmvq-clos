# DECISION W2R4 — Q6_K W4R4 T=4, nwarps 4→2 : NO-GO (29/10/2026)

## Question
Le kernel Q6_K `mul_mat_vec_q` W4R4 (type14, ~28.9–36.9 % du temps GPU-kernel
decode, cible in-scope dominante) est-il optimisable en **réduisant les warps
4→2** pour attaquer la pression register (96 regs, 5 blocks/SM) ?

## Hypothèse (et pourquoi elle était plausible)
- H3 (hoist du dépaquetage) = NO-GO à +2.29 % : la pression register ne venait
  pas des buffers de hoist (96 → 96, 0 spill).
- Le limiter résiduel identifié = **96 regs → 5 blocks/SM**, attribué aux
  **accumulateurs `tmp[4][4]` + la réduction warp de 4 warps**.
- Idée : avec 2 warps au lieu de 4, la réduction warp (tmp_shared) et le
  parallélisme intra-block diminuent → peut-être moins de regs par thread,
  plus de blocks/SM, meilleur hide latency.

## Candidat W2R4
- Patch `scratch/proto_v2/patch_w2r4.py` (idempotent, `--revert`) sur le fork
  dual-arch. Backup clean `bench/mmvq.cu.fork-w2-8035caf4.bak` (md5 `956b5a00d`).
- 3 modifications : (1) param template `nwarps_override=0` ; (2)
  `nwarps = nwarps_override>0 ? nwarps_override : calc_nwarps(...)` ; (3) branch
  dédiée dans le dispatch `case 4` (Q6_K) gated par `GGML_CUDA_Q6_W2R4`, qui
  instancie `mul_mat_vec_q<Q6_K, 4, false,false,false,false, rows=4, nwarps=2>`.
- Prod intact : `8035caf41` (vérifié avant/après).
- `.so` candidat : `dual-arch/lib/libggml-cuda-dual.so.w2-20261029` (md5 `a9eb6787`).

## Résultat SASS (le point central)
`cuobjdump --res-usage` sur les 2 instantiations (sm_70) :

| instantiation | REG | STACK | SHARED | LOCAL |
|---|---:|---:|---:|---:|
| W4 (prod, `...,4,0`) | **96** | 0 | 6144 | 0 |
| W2 (candidat, `...,4,2`) | **96** | 0 | 2048 | 0 |

**Réduire 4→2 warps ne réduit PAS les regs (96 → 96).** Le seul changement :
- SHARED 6144 → 2048 B : `tmp_shared[nwarps-1][4][4][32]` passe de 3→1 plan
  (3×4×4×32×4B = 6144 ; 1×4×4×32×4B = 2048).
- Block dim 128 → 64 threads (moins de threads pour hide la latence DRAM).

La pression register vient des **16 accumulateurs `tmp[4][4]` + le bloc q6_K
dépaqueté par (lane,kbx)** — indépendants du nombre de warps. L'hypothèse
« 96 regs = réduction warp » était **fausse** : la réduction warp se fait via
smem (pas regs), donc elle ne contribue pas aux 96.

## Validation numérique
`mb_mmvq` (dlopen, même RNG seed). Le mapping kbx par lane change (2 warps vs 4),
donc **pas bit-exact** (attendu). La validation porte sur la valeur, pas les bits :
- `val_rel` (row0, t=0) : prod = w2 = **4.04e-01 / 3.57e-01** (identiques, les deux
  corrects face à la réf CPU) → le candidat calcule la bonne matrice-vectorielle.
- dump hex row0 : 11–12/16 mots diff, relmax = bruit fp32 d'arrondi d'ordre
  d'accumulation (pas d'erreur fonctionnelle ; les sorties restent dans la plage).

## Résultats A/B microbench (3 rounds alternés, 100 iters, médiane, T=4)
| shape | prod µs | W2R4 µs | Δ | verdict |
|---|---:|---:|---:|---|
| **q6_f17408x5120** (dominante, 36.9 % prod) | 144.4 | 143.3 | **−0.76 %** | bruit |
| q6_f5120x17408 | 142.3 | 148.5 | **+4.36 %** | plus lent |

- Seuil de GO : **≥ 5 %** sur la shape dominante → **non atteint** (−0.76 %).
- La 2ᵉ shape est **plus lente** (+4.36 %) : moins de threads (64 vs 128) =
  moins de warps pour masquer la latence DRAM, alors que le kernel est
  latency/memory-bound (NCU recon2 : DRAM 59 %, NoElig 33 %, occ 27 %).
- Signes opposés selon la shape = **neutre global**, pas un gain.

Contrôle d'ordre (3 rounds, w2 d'abord, shape dominante) : prod 135.2 µs, W2R4
133.1 µs → **−1.55 %** — même signal léger, reproductible, toujours < 5 %.

## Verdict
**NO-GO.** Le levier « nwarps 4→2 sur Q6_K W4R4 T=4 » est **clos**.

- Réduire les warps n'abat pas la pression register (96 → 96, prouvé en SASS) :
  elle vient des 16 accumulateurs + le dépaquetage, pas de la réduction warp.
- Elle dégrade le hide latency (−50 % de threads) sur un kernel DRAM-bound →
  neutre à négatif.
- Confirmé par le précédent **42d9581** (nwarps 4→2, 17/10, A/B applicatif) :
  ~neutre sur le T=1 K-quant. Deux points indépendants convergent : **nwarps
  n'est pas un levier** sur ce GEMV.

## Conséquences pour la mission
- `DECISION_H3` + `mmvq_CLOS_note` s'étendent encore : sur le Q6_K W4R4 T=4,
  les leviers kernel testés sont maintenant (trafic : clos ; nwarps : clos ×2 ;
  hoist unpack : clos) → **aucun levier micro-kernel n'atteint 5 %**.
- La pression « 96 regs / 5 blocks/SM » est **structurelle** (16 accumulateurs
  `tmp[4][4]` + bloc q6_K) : l'attaquer exigerait de **changer le schéma de
  partition** (moins de kbx/lane, ou un autre découpage de la ligne), pas juste
  de tourner un paramètre. C'est un ré-écriture du kernel, au-delà du périmètre
  « bench A/B d'un paramètre ».
- Le decode reste au **mur HBM2** (mmvq_CLOS_note : 94–100 % du BW théorique).
  Tant que le poids q6/q8 est lu une fois par step, aucun micro-kernel n'a de
  headroom au-dessus du BW. L'unique levier avec headroom mesurable =
  **réduire les steps/token (acceptance MTP)**, pas le kernel mmvq.
- **Suite (même jour)** : `mmvq_weightload_CLOS_final_20261029.md` — les 3
  directions restantes (partition K / re-scope Q8_0-Q5_K / le reste hors périmètre)
  sont toutes tranchées → le périmètre « lecture des poids » est CLOS final.
